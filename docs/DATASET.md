# Dataset card

The data this project trains and evaluates on, and why it is split and scored the way it is. This card
tells the story as a chain of findings, each followed by the decision it led to. The decisions are
recorded in [`docs/adr/`](adr/); vocabulary is in [`GLOSSARY.md`](../GLOSSARY.md). The numbers come from
[`notebooks/01_dataset.ipynb`](../notebooks/01_dataset.ipynb) (EDA and the split),
[`results/label-audit.md`](../results/label-audit.md) (the test label audit) and
[`results/baselines.md`](../results/baselines.md).

## Schema

Each row is a user **query**, the **offered tools** (name, description, typed parameters) and the
**gold answer**: the list of calls that satisfies the query. Row 0:

```json
{
  "query": "Where can I find live giveaways for beta access and games?",
  "tools": [
    {
      "name": "live_giveaways_by_type",
      "description": "Retrieve live giveaways from the GamerPower API based on the specified type.",
      "parameters": {
        "type": {
          "description": "The type of giveaways to retrieve (e.g., game, loot, beta).",
          "type": "str",
          "default": "game"
        }
      }
    }
  ],
  "answers": [
    {"name": "live_giveaways_by_type", "arguments": {"type": "beta"}},
    {"name": "live_giveaways_by_type", "arguments": {"type": "game"}}
  ]
}
```

Types are Python-style strings (`str`, `int`, `List[float]`, `Callable`). Only the type string marks a
parameter optional (`int, optional`): xLAM also puts an example value under `default` on most required
parameters. The model sees the tools and the query through the Qwen3.5 chat template with thinking off
(ADR [0003](adr/0003-thinking-off.md)) and must answer with the JSON list and nothing around it.

## Shape

Figures for each of these are inline in [the notebook](../notebooks/01_dataset.ipynb), sections 2 to 4.

| | Value |
|---|---|
| Calls per row | mean 1.7, median 2, max 52 |
| Call pattern (train / test) | single 47% / 47% · multiple 32% / 31% · parallel 19% / 19% · mixed 2.5% / 2.4% |
| Tools offered per prompt | 1 to 8, median 3; the ones the answer doesn't call are distractors |
| Distinct functions called | 3,179, long-tailed: `search` 1,469 calls, thousands of API wrappers a handful each |
| Parameter types | mostly `str` and `int`; lists, tuples and `Callable` exist |
| Prompt tokens (p50 / p99 / max) | 471 / 1,440 / 3,525, measured with the chat template on 5,000 rows |
| Answer tokens (p50 / p99 / max) | 45 / 139 / 912 |

Training cost is mostly reading prompts, which the tool definitions dominate. On validation and test,
the longest prompt is 2,936 tokens and the longest answer 521, so `fc-eval`'s `--max-model-len 4096`
and `--max-tokens 1024` fit every row.

## Findings and decisions

### 1. Structurally clean

Every row parses, and every call names an offered tool with declared arguments
(`quality.unknown_calls` finds 0). APIGen checked answers by executing them, and it shows.

→ The two structural train filters planned in #6 (unparseable answers, calls to unknown functions)
remove nothing, and aren't applied.

The specs are loose, though: 2,752 values don't match their declared type (mostly floats in `int`
parameters, such as latitudes), and 3,757 calls leave out a parameter whose type says required. Both
point at imprecise specs, not wrong answers, so neither is filtered. They are worth knowing when reading
model errors.

### 2. Duplicates, contradictions and code-valued gold answers

| Problem | Found | Example |
|---|---:|---|
| Exact duplicate rows (beyond the first copy) | 375 | |
| Contradicting gold answers: same query, same tools, different answers | 21 rows in 10 groups | Bulldog as `is_id: 15` in one row and `14` in another |
| Code-valued arguments: a Python expression where a value is declared | 269 arguments in 224 rows | `"math.pi / 2"` for a `float`, `"[0.015] * 12"` for a `List[float]` |

A model can't be right on both sides of a contradiction, and a code-valued gold answer teaches it to copy text
instead of computing a value.

→ **Every train filter, in order:**

| Filter | Where | Rows removed |
|---|---|---:|
| Exact duplicates collapsed to their first copy | all rows, before splitting | 375 |
| Contradicting gold answers | train only | 20 |
| Code-valued arguments | train only | 213 |

The train counts are below the ones found because of overlaps: of the 224 code-valued rows, 10 sit in
validation and test and 1 is a duplicate; of the 21 contradicting rows, 1 is a duplicate.

Validation and test keep their gold answers as published, including 4 and 6 code-valued rows, so the
numbers stay comparable to other xLAM results (ADR [0002](adr/0002-test-labels-never-edited.md)). No gold answer
is ever rewritten.

### 3. Same query, different values, across splits

2,863 rows share their query text with another row, usually with a different toolset. And APIGen
generated many queries per tool, so the same sentence recurs with other values ("factorial of 7", "of
10").

→ Rows are grouped by normalized query and whole groups go to one split at random: test 2,000,
validation 1,000, train the rest (ADR [0001](adr/0001-train-validation-test-split.md)). **Leakage check:**
no normalized query appears in two splits (asserted in the notebook), and the call-pattern mix is
close in each split (single calls: 47.2% of train, 49.2% of validation, 47.4% of
test).

Templates and tools are still shared by construction: 16.5% of validation and 12.9% of test rows share a
query template with a train row, and only 2 validation and 4 test rows call a function train never
calls. These are new values for seen tools, not leaked answers, and removing them would cut a large part
of train. So **xLAM test measures filling new values into seen tools**, and generalization to unseen
tools is measured on BFCL.

Validation chooses checkpoints and settings; test only produces official numbers. With 2,000 test rows
the 95% interval is about ±2.2 points near 50%, and a slice is reported on its own only with at least
300 rows (ADR [0001](adr/0001-train-validation-test-split.md)).

### 4. Scouting: wrong-argument errors flat from 0.8B to 4B

On 1,000 rows, the 0.8B, 2B and 4B made 229, 256 and 224 wrong-argument errors (issue #4). Errors that
don't shrink with a model five times larger point at the gold answers: is "3% interest" `3` or `0.03`?

→ Audit the test gold answers, and audit **every** test row that any baseline gets wrong, not only the
teacher's errors (ADR [0002](adr/0002-test-labels-never-edited.md)). Auditing only the 2B and 4B errors
would have kept 18 unsound rows that only the student misses, lowering its `test-clean` score by 0.5
points and widening the teacher–student gap by 0.8.

### 5. Audit: at least 18.75% of test gold answers unsound; ceiling at most 81.25%

The rubric ([`docs/label-audit.md`](label-audit.md)) asks one question per row: would a careful person,
reading only the query and the tool specs, write this gold call? The verdict is `label_sound`,
`label_ambiguous` (one of several reasonable calls) or `label_wrong` (contradicts the query or specs, or
makes a value up). Labelling was blind to which model erred.

| | Rows |
|---|---:|
| Test | 2,000 |
| Every model right (assumed sound) | 742 |
| Audited | 1,258 |
| Label sound | 883 |
| Label ambiguous | 287 |
| Label wrong | 88 |
| **`test-clean`** | **1,625** |

The main causes of unsound labels: a format the spec leaves open (189 rows: `UK` vs `GB`, casing), a
query that doesn't fix the value (90: "last week" with no date), and wrong or made-up values (73:
`zuid: "jkl012"` for "agent D", `YOUR_API_KEY`). Rows every model gets right are assumed sound, so 18.75%
is a lower bound and 81.25% an upper bound on the ceiling: the best strict exact score an always-right
model could reach on raw test.

→ **`test-clean` (test minus ambiguous and wrong rows) is the target**, and every result is reported on
both test and `test-clean` (ADR [0002](adr/0002-test-labels-never-edited.md),
ADR [0005](adr/0005-train-and-validation-keep-label-noise.md)). The two tell different stories:

| | Test | `test-clean` |
|---|---:|---:|
| Student, Qwen3.5-0.8B | 46.4 | 55.1 |
| Teacher, Qwen3.5-2B | 65.3 | 76.9 |
| **Gap** | **18.9** | **21.8** |

Per-row verdicts: [`data/audit/test_labels.csv`](../data/audit/test_labels.csv). Full breakdown and
method: [`results/label-audit.md`](../results/label-audit.md).

### 6. Blind review: 9 of 30 disagreements

The maintainer relabelled 30 random audited rows blind. 9 changed soundness, over the threshold of 3
that the rubric set for "too loose".

→ The rubric was tightened. Of the nine: three came from the verdict's old name, `model_wrong`, which
misled the reviewer and is now `label_sound`; one from a bug in the review page, which rounded a
19-digit id in JavaScript; four from a format the spec leaves open, now a rule (the row is ambiguous);
and one from outside knowledge, now a rule (a value with exactly one real-world answer, like Inception's
IMDb id, is sound). Under the tightened rubric every one of the nine keeps its audit verdict. A tenth
row changed only its unsound verdict, a made-up `zuid: "jkl012"`; the rule that a made-up value is wrong,
not ambiguous, came from it, and a rescan moved 13 such rows from ambiguous to wrong without changing
`test-clean`.

This is shown as is: the rules were settled with the reviewer after comparing the disagreements, so it
isn't a second independent check. A fresh blind sample under the tightened rubric would be one. Details:
[`results/label-audit.md`](../results/label-audit.md#review) and the
[review sheet](../results/label-audit-review.md).

### 7. Train likely has about 10,000 unsound labels too

Test is a random sample of xLAM, so train very likely has a similar share of unsound labels: roughly
10,000 of its 56,392 rows. Most of them need judgement that no rule captures (is `UK` acceptable?).

→ ADR [0005](adr/0005-train-and-validation-keep-label-noise.md):

- **Train keeps its gold answers.** Rows leave train only through filters that detect a problem without
  judgement. Placeholders and values found in neither query nor spec are candidates, measured on train
  first (#17).
- **Validation is not audited** unless a method's gain on raw test is much larger than its gain on
  `test-clean`, the sign that it learned xLAM's quirks.
- **Teacher outputs are filtered with lenient exact**, so the filter keeps the teacher's defensible
  answers (`GB`, a default left out) instead of only the ones that copy gold's quirks.

### 8. Explicit defaults in 7.7% of rows

6,882 gold arguments in 4,633 rows (7.7%; 161 test rows) pass an optional argument at its declared
default or as `null`. A model that leaves it out makes the same call by the spec, but strict exact match
marks it wrong. Many xLAM defaults look like example values copied from API docs, so "same call" holds by
the spec, not necessarily for the real API.

→ `lenient_exact` is reported next to strict `exact` (#15). It ignores optional arguments at their
default or `null`, on either side. Strict stays the headline. Gold answers stay as published.

## BFCL: the unseen-tools eval

xLAM test calls only tools that train also calls (finding 3), so a second eval checks generalization to
new tools: 1,000 non-live, single-turn rows of the
[Berkeley Function-Calling Leaderboard](https://huggingface.co/datasets/gorilla-llm/Berkeley-Function-Calling-Leaderboard)
v3 (revision `61fc0608cfd831fcfbbaa676ebdfef0ed963eeda`, Apache-2.0): simple 400, multiple 200,
parallel 200, parallel_multiple 200. Only 44 of them call a function some xLAM train answer also calls.

Each BFCL spec is converted to xLAM's format, so a drop on BFCL reflects new tools rather than a new
prompt. BFCL lists the acceptable values for each argument, and a prediction scores `exact` when its
calls pair one-to-one with the gold calls and every value is acceptable under xLAM's strict comparison.
Results are reported overall, for simple (400) and for the other three merged (600), by the 300-row
rule. Nothing is chosen on BFCL. Conversion, scoring rules and caveats: [`docs/bfcl.md`](bfcl.md).

## Reproduce

```bash
uv run hf auth login     # after accepting the dataset's terms
uv run jupyter nbconvert --to notebook --execute --inplace notebooks/01_dataset.ipynb   # writes data/splits.json
uv run fc-eval --model Qwen/Qwen3.5-0.8B --split test-clean
```

The split is deterministic given the pinned revision; `data/splits.json` is committed, so evals don't
need to rebuild it.
